# Greeo backend working rules

You are my pair-programmer for the backend of “Greeo”, an entry in the Amazon Developer Hackathon 2026, Alexa+ track. I want to understand every line, so how you work matters as much as the code.

## What Greeo is

Greeo is an Alexa+ agent that transforms the news into memorable, voice-first tales inspired by African oral storytelling traditions, including griot traditions where appropriate. The telling is warm, rhythmic and vivid, with verified African proverbs woven into the story when they genuinely fit, followed by a short moral or reflection. It never just reads news word for word. The telling is built on established, cited facts, so the story is memorable and the truth stays checkable. After the tale, users can ask for the truth behind it: FACTS, CONTEXT, PERSPECTIVES, SOURCES, and an explanation of each proverb (culture, meaning, source). Users choose a tone (light, balanced, serious). Greeo remembers what a user heard, saved, and where they stopped.

Signature experience: TALE (in beats) -> MORAL/REFLECTION -> PROVERBS explained -> FACTS -> CONTEXT -> PERSPECTIVES -> SOURCES.

The sequence is Greeo’s information architecture, not a forced conversation. After or during a tale, the user may naturally jump to any available truth layer (for example facts, context, perspectives, proverb meaning, or sources) and later resume the tale.

Do not use “Tales by Moonlight” as a product name or brand; say “moonlight tale tradition” instead.

## Architecture

Six compose services: web (Django + DRF, admin, simulator API), mcp (MCP server, separate process, same codebase and DB), worker (Celery), beat (Celery beat), postgres, and redis.

Django apps under `backend/apps/`: core, news, stories, wisdom, memory, llm, mcp_server, simulator.

Data flow: feeds/curated files -> articles/evidence -> event clusters -> editorial workflow (facts, context, perspectives -> proverb selection -> tellings per tone -> checker agent -> revise once -> validation) -> published. MCP tools only read precomputed data; no LLM calls occur on the hot path.

During the vertical-slice phase, one human-curated real event is the golden test fixture: it enables the complete Greeo experience to be built before live ingestion exists. It is not a product limitation. Once the editorial pipeline exists, Greeo must ingest current news and automatically generate validated, publishable events. The curated event remains the deterministic fallback and regression fixture.

## Content and product rules

1. Proverbs are never generated by an LLM or by the agent. Writers output slot markers such as `{{P1}}`; server code substitutes the exact text of a verified proverb. Only proverbs with `verification_status == "verified"` may be served. Test fixtures use obvious fake text such as “TEST PROVERB 1”.
2. The initial curated demo event’s real-world event content, evidence, source URLs, verified proverbs, and approved telling content are supplied and curated by the project owner, then loaded from `data/demo_event.yaml`. The agent must not author those materials. Later, the editorial pipeline may use an LLM only to generate derived candidate content—tale beats, context, perspectives, reflections, and proverb-selection decisions—from supplied/stored evidence and verified proverb candidates. Every generated result must pass evidence checks, deterministic validation, checker review, one bounded revision, and publication gates. An LLM must never invent real-world sources/evidence or traditional proverbs. Test fixtures remain visibly synthetic (fictional places, “SYNTHETIC EVENT”) and are flagged `is_synthetic`.
3. A telling may use vivid language, rhythm, repetition, and imagery. It may not add facts, invent scenes about real people, put invented dialogue or quotations in anyone’s mouth, or present Greeo’s own images as traditional tales. No quotation marks are permitted in beats.
4. No faux dialect, caricature, or treatment of Africa as one voice. Cultural attribution comes only through the proverb’s specific culture. The jointly written `docs/GRIOT_STYLE_GUIDE.md` governs voice.
5. Use only news sources whose terms have been recorded as reviewed. Store headline, cleaned URL, source name, date, and a snippet of at most 300 characters. Never store or output article body text. Strip tracking parameters from every URL.
6. No stealth or evasion: use an honest User-Agent, respect rate limits and `robots.txt`, and stop on 403/429.
7. Spoken text is at most 75 words per reply (about 30 seconds), presents at most 5 options, and avoids technical words. A tale is delivered in beats.
8. Identity comes from the request authentication, never from a tool argument. Every memory query filters by user.
9. Every fact, context item, and perspective links to evidence.
10. Never describe scripted behaviour as LLM behaviour. Traces record `host_mode = mock | llm`.
11. No prototype code is used. `docs/notes/prior-prototype.md` describes the earlier web prototype for context only; do not recreate its patterns where they conflict with these rules (for example, fetching article pages or letting a model choose proverbs).
12. “Griot” is a specific cultural/historical tradition, not a synonym for all African storytelling. Product copy says Greeo is inspired by African oral storytelling traditions; use “griot” only as a specific influence where culturally appropriate and supported by the style guide.
13. A moral/reflection may express a broad human theme, but must not judge a real political actor, organisation, community, disputed claim, or side as right/wrong; infer motives; or turn a contested event into a lesson unsupported by evidence. For sensitive or contentious events, prefer a neutral reflection or omit it.
14. The layer order is not mandatory navigation. Users may interrupt a tale or jump directly to facts, context, perspectives, proverb explanation, or sources, then resume where they stopped.

## How to work

1. Take small steps. Do exactly the requested prompt, then stop and wait.
2. Verify, do not guess. Before using a library API, check the installed version’s source or documentation. Never invent function names.
3. Do not add a dependency without first stating its name, version, and reason. Pin versions.
4. Write boring, readable code: type hints, short functions, a service layer (views/tasks/tools stay thin; logic is in `services.py`), and docstrings explaining why.
5. Every feature ships with tests. Run them and show their output.
6. Use configuration only through environment variables; keep `.env.example` current; never commit secrets.
7. Commit after each logical step with a clear message.
8. If a document, SDK, or tool wastes more than 10 minutes, append a genuine entry to `docs/FRICTION_LOG.md` covering task, steps, expected versus actual, severity, workaround, and suggestion.
9. Write a walkthrough at the end of every phase.
